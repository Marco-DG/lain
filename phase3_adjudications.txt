# ── new-more-precise: THE CORPUS IS WRONG HERE ────────────────────────────────
# Two fail-tests encode an OLD-ENGINE LIMITATION as a required rejection. Both programs are
# SAFE; a correct NLL checker accepts them. They were found by re-judging every "gap" on its
# merits instead of assuming the old engine was right — the bias the C1 gate was built to
# expose, and which I had nonetheless applied to all 25 divergences at first.
#
# (1) mut_plus_nested_shared_fail: `scale(var v, length(v))` — the canonical TWO-PHASE
#     borrow, i.e. `v.push(v.len())`. `length(v)` completes during argument evaluation,
#     before `scale` writes; there is no aliasing, and the hoisted form (`f = length(v);
#     scale(var v, f)`) compiles and runs identically. The corpus CONTRADICTS ITSELF: the
#     same pattern is REQUIRED TO PASS by tests/ownership/two_phase_borrow_pass.ln
#     (`push_n(var v, v.cap)`). The only difference is that the shared read goes through a
#     call rather than a field access — precisely the old engine's documented blind spot
#     ("two-phase covers direct-read args, NOT nested-call args"). The new engine accepts by
#     construction: a by-value `i32` argument is a COPY, and a copy is not a loan.
#     ⇒ at 3.5 this test INVERTS to a pass-test.
#
# (2) multi_var_param_fail: `var ref = pick_x(var da, var db)` then `read_data(db)`, where
#     `pick_x(var a, var b) var i32` returns `var a.x`. The test asserts db "is still
#     borrowed by ref" — FALSE. Only the returned reference's loan outlives the call, and it
#     roots in `a`; db's mutable borrow ends at return. Rust accepts the analogue
#     (`fn pick<'a>(a:&'a mut D, b:&mut D)->&'a mut i32`). The old engine over-rejects by
#     assuming a returned reference borrows EVERY reference parameter.
#     ⇒ at 3.5 this test INVERTS to a pass-test.
#
# Judging (2) is what exposed a REAL UNSOUNDNESS in the new engine (now fixed): the borrow
# source was GUESSED from the signature ("first mutable reference param"), so `return var b.x`
# charged the loan to `a` and lost every conflict on `b`. It is now INFERRED from the body
# (bor_ret_borrow_mask). Doubting the corpus found a bug in the checker, not just the corpus.
tests/ownership/mut_plus_nested_shared_fail.ln            NEW-ACCEPTS  new-more-precise
tests/ownership/multi_var_param_fail.ln                   NEW-ACCEPTS  new-more-precise

# ── new-incomplete-borrow ─────────────────────────────────────────────────────
# The LOAN-SITE generalisation closed 3 (cross_stmt_borrow_write, owner_reassign,
# direct_var_borrow). Loans had only ever been created AND checked at call arguments, so the
# conflict rule (design §1.4) was silently restricted to calls. It is over ACCESSES:
#   • a loan is also created by a DIRECT address-of whose result is PARKED IN A SLOT
#     (`var ref = var d.value`) — requiring the slot is what separates a borrow from ordinary
#     field/element access, so `a[i] = v` does not conflict with itself
#   • a conflict is also raised by a DIRECT STORE to an overlapping place inside the region
#     (`d.value = 99`, and whole-owner reassignment `d = D(99)`)
#
# What remains is NOT one cluster — the old engine reports these under four different codes,
# and only match_borrow_mut is a borrow conflict at all:
#   match_borrow_mut  E004 — a real conflict, through a `case` binding (phase B: reborrows)
#   struct_field_dangling  E010 — escape through a struct field holding a string-literal local
#   block_scope  E003, elif_borrow  E016 — LEAK/consistency on one branch, not borrows;
#     they sit in this section only because that is where they were first triaged.
tests/ownership/block_scope_fail.ln                       NEW-ACCEPTS  new-incomplete-borrow
tests/ownership/borrow_fail.ln                            NEW-ACCEPTS  new-incomplete-borrow
tests/ownership/elif_borrow_fail.ln                       NEW-ACCEPTS  new-incomplete-borrow
tests/types/match_borrow_mut_fail.ln                      NEW-ACCEPTS  new-incomplete-borrow
# escape analysis exists but misses this shape (field borrows a string-literal local)
tests/ownership/struct_field_dangling_fail.ln             NEW-ACCEPTS  new-incomplete-borrow

# ── new-incomplete-linearity ──────────────────────────────────────────────────
# MOVE-ON-ASSIGN closed 3 of these (move_then_use, linear_copy_double_free,
# struct_linear_field): reading a LINEAR value out of its slot into another slot is a
# transfer, not a copy. What remains splits into three precise sub-gaps:
#
# (a) UNCONSUMED OWNED VALUES — the old engine is INCONSISTENT here, so these are not
#     straightforward gaps. See CORPUS_CORRECTIONS.md C-3: borrow_pass REQUIRES an
#     unconsumed owned `Counter{i32}` to be ACCEPTED while rich_diagnostics REQUIRES an
#     unconsumed owned `Resource{i32}` to be REJECTED — same shape, opposite verdicts, the
#     discriminator being how the local was initialised (a constructor infers MODE_OWNED, a
#     call result does not) rather than anything about the value.
#     C7 (the owns-bit) is now DONE: IrValue.owns separates the binding's ownership from the
#     type's linearity, which is what made the 4 shared-borrow false positives go away. The
#     leak rule is now `owned AND has a release obligation` (transitively owns a ptr/slice —
#     "non-trivial destructor"), which also CAUGHT A CLASS THE OLD NARROWING MISSED: a struct
#     owning a heap pointer, never freed, was untracked because only ptr/slice slots were.
#     What remains is a POLICY question (error vs implicit drop), deferred to Stage V.
tests/ownership/consume_before_return_fail.ln             NEW-ACCEPTS  new-incomplete-linearity
tests/ownership/rich_diagnostics_fail.ln                  NEW-ACCEPTS  new-incomplete-linearity
#
# (b) DEFER. `defer drop(mov r)` commits r's single consumption at scope exit; consuming
#     again (or deferring twice) is a double free. The IR does not model scope-exit edges,
#     so neither is visible. Needs defer lowered as a real CFG edge — an IR completeness
#     item, not an analysis one.
tests/ownership/defer_double_consume_fail.ln              NEW-ACCEPTS  new-incomplete-linearity
tests/ownership/defer_double_defer_fail.ln                NEW-ACCEPTS  new-incomplete-linearity
#
# (c) MISCLASSIFIED — `owner_reassign` is a BORROW error (E004), not a linearity one: a
#     whole-owner STORE while a loan is live. Same root cause as cross_stmt_borrow_write /
#     direct_var_borrow — loans are created only at call arguments, so a direct store is
#     invisible. Fixed by the same change; kept here only so the count is honest.
tests/ownership/owner_reassign_fail.ln                    NEW-ACCEPTS  new-incomplete-linearity
