# ── new-more-precise: THE CORPUS IS WRONG HERE ────────────────────────────────
# Two fail-tests encode an OLD-ENGINE LIMITATION as a required rejection. Both programs are
# SAFE; a correct NLL checker accepts them. They were found by re-judging every "gap" on its
# merits instead of assuming the old engine was right — the bias the C1 gate was built to
# expose, and which I had nonetheless applied to all 25 divergences at first.
#
# (1) mut_plus_nested_shared_fail: `scale(var v, length(v))` — the canonical TWO-PHASE
#     borrow, i.e. `v.push(v.len())`. `length(v)` completes during argument evaluation,
#     before `scale` writes; there is no aliasing, and the hoisted form (`f = length(v);
#     scale(var v, f)`) compiles and runs identically. The corpus CONTRADICTS ITSELF: the
#     same pattern is REQUIRED TO PASS by tests/ownership/two_phase_borrow_pass.ln
#     (`push_n(var v, v.cap)`). The only difference is that the shared read goes through a
#     call rather than a field access — precisely the old engine's documented blind spot
#     ("two-phase covers direct-read args, NOT nested-call args"). The new engine accepts by
#     construction: a by-value `i32` argument is a COPY, and a copy is not a loan.
#     ⇒ at 3.5 this test INVERTS to a pass-test.
#
# (2) multi_var_param_fail: `var ref = pick_x(var da, var db)` then `read_data(db)`, where
#     `pick_x(var a, var b) var i32` returns `var a.x`. The test asserts db "is still
#     borrowed by ref" — FALSE. Only the returned reference's loan outlives the call, and it
#     roots in `a`; db's mutable borrow ends at return. Rust accepts the analogue
#     (`fn pick<'a>(a:&'a mut D, b:&mut D)->&'a mut i32`). The old engine over-rejects by
#     assuming a returned reference borrows EVERY reference parameter.
#     ⇒ at 3.5 this test INVERTS to a pass-test.
#
# Judging (2) is what exposed a REAL UNSOUNDNESS in the new engine (now fixed): the borrow
# source was GUESSED from the signature ("first mutable reference param"), so `return var b.x`
# charged the loan to `a` and lost every conflict on `b`. It is now INFERRED from the body
# (bor_ret_borrow_mask). Doubting the corpus found a bug in the checker, not just the corpus.

# ── new-over-strict: CLOSED by phase D ────────────────────────────────────────
# RESOLVED (the entry below is kept for the reasoning, the test now AGREES). The octagon is
# wired into `ir_place_index_disjoint_fn`, so `swap2(var a[i], var a[j])` with distinct
# indices is accepted while `swap2(var a[i], var a[i])` still conflicts. Pinned by five unit
# cases in test_borrow.c including the RELATIONAL one — `a[p]` vs `a[q]` under `p<q`, where
# neither index has a value and the octagon proves they differ anyway. THAT is the case Rust
# cannot express: its borrow checker has no numeric domain to ask.
#
# Historical motivation:
# The new engine REJECTS `swap2(var a[i], var a[j])` with i=1, j=5 — two mutable borrows of
# provably DISTINCT elements. Its conflict rule is right to be conservative by default
# (ir_place_index_provably_disjoint returns false without a numeric bridge), and that same
# default is what makes it CATCH `swap2(var a[i], var a[i])`, which the old engine accepted
# and emitted as two aliasing `restrict` pointers — a demonstrated miscompile (-O0 226 vs
# -O2 116, now fixed and locked by coarg_alias_element_fail).
#
# So this is the precision half of the same rule, and it is exactly borrow phase D: fill
# `ir_place_index_disjoint_fn` from the octagon, which can prove i≠j. ★ This is the
# project's most defensible beyond-Rust claim — Rust cannot distinguish a[i] from a[j] at
# all, which is why `split_at_mut` needs `unsafe`. The seam exists (ir/place.h); what it
# needs is a query POINT, since the octagon state is per-block and the hook currently takes
# only the two values.

# ── new-incomplete-borrow ─────────────────────────────────────────────────────
# The LOAN-SITE generalisation closed 3 (cross_stmt_borrow_write, owner_reassign,
# direct_var_borrow). Loans had only ever been created AND checked at call arguments, so the
# conflict rule (design §1.4) was silently restricted to calls. It is over ACCESSES:
#   • a loan is also created by a DIRECT address-of whose result is PARKED IN A SLOT
#     (`var ref = var d.value`) — requiring the slot is what separates a borrow from ordinary
#     field/element access, so `a[i] = v` does not conflict with itself
#   • a conflict is also raised by a DIRECT STORE to an overlapping place inside the region
#     (`d.value = 99`, and whole-owner reassignment `d = D(99)`)
#
# What remains is NOT one cluster — the old engine reports these under four different codes,
# and only match_borrow_mut is a borrow conflict at all:
#   match_borrow_mut  E004 — a real conflict, through a `case` binding (phase B: reborrows)
# borrow_fail and elif_borrow are now CLOSED too — a MOVE is an access (a consuming parameter
# invalidates the place, so it conflicts with any overlapping one), and a second MUST-moved
# lattice (intersection merge) beside the MAY one gives E016 = "moved on some paths, not all".
# block_scope is CLOSED by per-field linear state (a consumption MASK per slot) plus failing
# CLOSED on an opaque linear struct. ONE remains:
#   match_borrow_mut — CLOSED (IR_BORROW/IR_BORROW_END). The extent is stated by the
#     CONSTRUCT because no value's liveness expresses it: nothing in the arms reads the
#     borrow, so a liveness-derived region is empty and `42: x = 99` looked legal. The region
#     is a CFG REACHABILITY set, not a span of the flattened instruction list — the match's
#     join block (holding borrow_end) is emitted BEFORE the arms, so a linear scan ended the
#     region before reaching the writes it must catch. THE BORROW COLUMN IS NOW EMPTY.
# struct_field_dangling is CLOSED: two fixes, both found by taking it seriously rather than
# filing it. Lowering now gives a mutable string binding its OWN storage (which also fixed a
# real segfault — see CORPUS_CORRECTIONS/commit b56aa24), so the slice honestly roots in an
# alloca; and escape analysis follows provenance through a LOAD from a singly-stored slot.

# the corpus test's own header said was needed before it could flip. Destructuring an owned
# sum MOVES the resource out of the scrutinee and into the payload binding; the binding then

# ── overflow: the old engine is INCONSISTENT, and silently wrong on one side ──────────────
# `--engine=ir-full` rejects ~121 corpus pass-programs on numeric obligations, and the first
# reading of that number ("the new engine is over-strict") is wrong for a large share of them.
#
#   func add(a i32, b i32) i32 { return a + b }        → OLD ENGINE REJECTS  [E086]
#   func sum(p Point)     i32 { return p.x + p.y }     → OLD ENGINE ACCEPTS
#
# Same expression, same types, different SOURCE of the operands: a parameter is range-checked,
# a struct FIELD is not. What the old engine emits for the accepted one is
#       return ((int64_t)(p->x) + (int64_t)(p->y));
# — it widens the arithmetic to avoid the UB, then narrows on return. EXECUTED:
#       p.x = 2147483647 ; p.y = 1 ; sum(p)   →   prints  -2147483648
# A compiler whose whole claim is prove-or-reject silently returns the wrong number.
#
# So the new engine REFUSING these is old-unsound, not new-over-strict. It cannot become a
# corpus fail-test while the old engine is authoritative; it inverts at 3.5.
#
# The genuinely imprecise part of that 121 is a different family — loop counters (`i = i + 1`
# under `i < n`), where the bound exists and the new engine should find it. Tracked separately;
# do not conflate the two when reading the gate's number.
