\chapter{Statements}
\label{sec:09-statements}
\index{statement}

\pnum
A statement is a unit of execution.  Statements are terminated by a line feed
or a semicolon (\S\,\ref{sec:lex.whitespace}); the semicolon is used to place
several statements on one line.  The grammar production for
\gramref{statement} is in Annex~A.

\section{Block statement}
\label{sec:stmt.block}
\index{block statement}

\pnum
A block statement \lain{\{ stmts... \}} creates a new scope
(\S\,\ref{sec:basics.scopes}) and executes each contained statement in
order.  Names declared inside a block are not accessible outside it.

\section{Immutable declaration}
\label{sec:stmt.decl}
\index{immutable declaration}

\pnum
\lain{name [Type] = expr} declares and initializes an immutable binding.
The type may be omitted (inferred from the initializer).  The binding
cannot be reassigned after initialization.

\begin{laincode}
type Point {
    x i32
    y i32
}

func main() i32 {
    x i32 = 42          // explicit type
    y = 10              // type inferred (i32)
    p Point = Point(1, 2)
    return 0
}
\end{laincode}

\begin{constraint}
  An immutable declaration requires an initializer expression: an immutable
  binding must have a definite value at its point of declaration.
\end{constraint}

\begin{constraint}
  When a type annotation is present, the type of the initializer shall be
  compatible with the declared type (\S\,\ref{sec:types.compat}).
\end{constraint}

\begin{note}
  When the type is omitted, the distinction between declaration and
  reassignment is resolved by scope: \lain{x = 5} where \lain{x} is not
  yet declared creates a new immutable binding; where \lain{x} is already
  declared as \lain{var}, it is a reassignment.
\end{note}

\section{Mutable variable declaration}
\label{sec:stmt.var}
\index{variable declaration}

\pnum
\lain{var name Type = expr} declares a mutable variable.  Mutable variables
can be reassigned.  The type may be omitted if it can be inferred from the
initializer.

\begin{laincode}
var counter i32 = 0
counter = counter + 1       // OK: var is mutable

var buf u8[256]              // OK: type present; unassigned until written
                            // (reading before a write is [E005])
\end{laincode}

\begin{constraint}
  A mutable declaration shall include either an explicit type annotation
  or an initializer expression.  A declaration with neither is
  \illformed{}~(\diagcode{E100}).
\end{constraint}

\begin{constraint}
  When both a type annotation and an initializer are present, the type of
  the initializer shall be compatible with the declared type
  (\S\,\ref{sec:types.compat}).
\end{constraint}

\section{Assignment statement}
\label{sec:stmt.assign}
\index{assignment statement}

\pnum
An assignment statement \lain{lvalue = expr} stores the value of
\textit{expr} into the storage designated by \textit{lvalue}.
An assignment target without a type annotation is always a reassignment,
never a declaration.

\begin{constraint}
  The left-hand side shall be a mutable lvalue (\S\,\ref{sec:basics.lvalues}).
  Assigning to an immutable binding, or to an element or field of one, or to a module
  constant, is \illformed{}~(\diagcode{E009}).  So is lending such a place as \lain{var},
  as an argument (\lain{f(var a)}) or a reference binding (\lain{var r = var x}).  An
  array or slice \emph{parameter} is an output reference: its elements may be written, so an
  immutable array (or a module constant) shall not be passed to one that the callee writes,
  directly or through a further call; an \lain{extern} is assumed to write it~(\diagcode{E009}).
  Immutability belongs to the \emph{storage}: no write shall reach an immutable binding's
  storage, or a module constant's, by any path, whether through a slice or reference kept in a
  \lain{var} binding (\lain{var s = xs[0..2]  s[0] = 9}), handed back by a call
  (\lain{w(id(xs[0..2]))}), or held in a struct whose callee writes through it, other than the
  binding's own initialiser~(\diagcode{E009}). A copy (\lain{var c = xs}) is new storage and
  may be written.
\end{constraint}

\begin{constraint}
  Overwriting a linear variable whose current value has not been consumed
  would leak that value.  Such an assignment is
  \illformed{}~(\diagcode{E021}).
\end{constraint}

\begin{note}
  Assigning to a linear variable after its previous value has been consumed
  (e.g., loop reassign-and-consume pattern) is permitted.  The implementation
  resets the variable's linear state to Unconsumed after a legal overwrite.
\end{note}

\begin{example}
\begin{laincode}
import std.fs.{open_file, close_file}

func main() int effects io, raises, alloc {
    var f = open_file("data.txt", "r")
    close_file(mov f)               // f is now Consumed
    f = open_file("data.txt", "r")  // OK: overwriting Consumed state
    close_file(mov f)
    return 0
}
\end{laincode}
\end{example}

\section{Expression statement}
\label{sec:stmt.expr}
\index{expression statement}

\pnum
An expression followed by a statement terminator is an expression
statement.  The value of the expression is discarded.

\section{If statement}
\label{sec:stmt.if}
\index{if statement}

\pnum
\lain{if cond \{ body \} [else if cond \{ body \}]... [else \{ body \}]}
evaluates \textit{cond}; if true, executes the then-body; otherwise,
tests the \lain{else if} clauses in order; if none matches, executes the
\lain{else} body (if present).

\begin{constraint}
  \textit{cond} shall have type \lain{bool}, or an integer type, or an optional that
  narrows (\S\,\ref{sec:types.bool}).  An integer in condition position is false when
  zero and true otherwise.
\end{constraint}

\pnum
\textbf{Range refinement}: inside the then-branch of \lain{if x < N \{ \}},
the value range analysis (\S\,\ref{sec:13-vra}) knows that
$x \in (-\infty, N-1]$; inside the else-branch, $x \in [N, +\infty)$.

\pnum
\textbf{In-guard}: when \textit{cond} contains or is an \lain{in}
expression (\S\,\ref{sec:expr.in}), the in-guard is active inside the
then-branch only.

\pnum
\textbf{Branch consistency}: if one branch consumes a linear variable,
all branches shall consume it.  If branches disagree on the linear state
of a variable from the enclosing scope, the program is
\illformed{}~(\diagcode{E003}).

\section{While statement}
\label{sec:stmt.while}
\index{while statement}

\pnum
\lain{while cond \{ body \}} repeatedly evaluates \textit{cond} and, if
true, executes \textit{body}.

\begin{constraint}
  A \lain{while} loop inside a \lain{func} shall be bounded: it shall carry a
  \lain{decreasing} measure, or the implementation shall be able to infer one
  from its condition (\S\,\ref{sec:stmt.while.infer}).  A loop for which no
  measure is present and none can be inferred is
  \illformed{}~(\diagcode{E011}).
\end{constraint}

\begin{constraint}
  \textit{cond} shall have type \lain{bool}, or an integer type, or an optional that
  narrows (\S\,\ref{sec:types.bool}).  An integer in condition position is false when
  zero and true otherwise.
\end{constraint}

\pnum
\textbf{In-guard}: when \textit{cond} contains or is an \lain{in}
expression, the in-guard is active inside the loop body for each
iteration.

\subsection{Bounded while statement}
\label{sec:stmt.while.bounded}
\index{bounded while loop}
\index{decreasing measure}

\pnum
\lain{while cond decreasing M \{ body \}} is a bounded loop.  In addition
to the while semantics above, the implementation shall statically verify:

\begin{enumerate}
  \item \textbf{Bounded below} (\diagcode{E082}): the implementation shall
        prove that $M$ cannot decrease without limit.
  \item \textbf{Analyzable measure} (\diagcode{E082}): $M$ shall be in a form
        the implementation can analyse.  A measure it cannot analyse at all ---
        including a constant, or one over variables the body never assigns ---
        is rejected, and so is one that is merely not provably well-founded:
        both are \diagcode{E082}, because one termination obligation with one
        source reports them.  (Two earlier codes, \texttt{E080} and
        \texttt{E081}, separated these sub-cases when a second termination
        checker existed in the front end; they are withdrawn, see Annex B.)
  \item \textbf{Strict decrease} (\diagcode{E082}): the implementation
        shall prove that every execution of \textit{body} strictly
        decreases the value of $M$, \emph{except} along paths that leave the
        loop via \lain{break} or \lain{return}.  A branch that unconditionally
        exits the loop never iterates again, so it is exempt from the decrease
        requirement; only paths that loop back need decrease $M$.  (A
        \lain{continue} re-evaluates \textit{cond} and thus loops back, so it
        is \emph{not} an exit.)
\end{enumerate}

\pnum
A bounded \lain{while} loop is permitted inside a \lain{func} because the
implementation has statically verified termination.

\pnum
The following patterns are accepted by the standard verification algorithm:

\begin{longtable}{@{}lll@{}}
\toprule
\textbf{Condition} & \textbf{Measure} & \textbf{Why} \\
\midrule
\endfirsthead
\toprule
\textbf{Condition} & \textbf{Measure} & \textbf{Why} \\
\midrule
\endhead
\bottomrule
\endlastfoot
\lain{i < n}    & \lain{n - i}      & $i$ increases $\Rightarrow$ measure decreases \\
\lain{i <= n}   & \lain{n - i}      & $i$ increases toward the inclusive bound \\
\lain{n > 0}    & \lain{n}          & $n$ decreases directly \\
\lain{i > k}    & \lain{i - k}      & $i$ decreases toward $k$ \\
\lain{a < b}    & \lain{b - a}      & either $a$ increases or $b$ decreases \\
\lain{i in 0..arr.len} & \lain{arr.len - i}& the range's upper bound gives $i < \texttt{arr.len}$ \\
\end{longtable}

\pnum
Beyond the syntactic patterns above, the standard verification algorithm
also accepts a measure variable that is set to a constant provably below the
loop's guaranteed lower bound (e.g.\ \lain{j = 0} inside \lain{while j > 0}),
and unsigned measures driven by \lain{v = X \% v}, \lain{v = v / D}, or
\lain{v = v >> C}.

\subsection{Measure inference}
\label{sec:stmt.while.infer}
\index{measure inference}

\pnum
The \lain{decreasing} clause \emph{may be omitted}.  When it is, and the loop
appears in a context that requires termination (a \lain{func} body), the
implementation shall attempt to \emph{infer} a measure from \textit{cond}
using the correspondences above: a relational condition \lain{i < n},
\lain{i <= n}, \lain{i > k}, or \lain{i >= k} yields the candidate
\lain{n - i} (respectively \lain{i - k}); a two-variable bound \lain{lo < hi}
yields \lain{hi - lo}; and a range membership \lain{i in 0..n} yields \lain{n - i}.

\pnum
An inferred measure is subject to the \emph{identical} verification as an
explicit one (non-negativity, analyzability, strict decrease).  If no
candidate can be inferred, or the candidate fails verification, the loop is
\illformed{}~(\diagcode{E011}): the programmer shall then supply an explicit
\lain{decreasing} clause or restructure the loop.  Inference is therefore a
convenience only; it never accepts a loop that an explicit measure could not.

\begin{example}
\begin{laincode}
func count(n int) int {
    var i = 0
    while i < n {          // measure `n - i` is inferred
        i = i + 1
    }
    return i
}
\end{laincode}
\end{example}

\begin{rationale}
  Bounded loops bridge the gap between pure functions (which must terminate)
  and the common pattern of finite-input state machines (lexers, parsers)
  that are provably terminating.  For the overwhelmingly common counting and
  scanning loops the measure is mechanical, so it is inferred; the
  \lain{decreasing} keyword remains available to state a termination argument
  the compiler cannot infer, which it then verifies.
\end{rationale}

\section{Return statement}
\label{sec:stmt.return}
\index{return statement}

\pnum
\lain{return [expr]} terminates execution of the current function or
procedure and transfers the value of \textit{expr} (if present) to the
caller.

\begin{constraint}
  At the point of a \lain{return}, all linear variables in scope shall
  have been consumed.  A live (Unconsumed) linear variable at \lain{return}
  is \illformed{}~(\diagcode{E003}).
\end{constraint}

\pnum
A \lain{return} expression may be prefixed with \lain{mov} or \lain{var}:
\lain{return mov x} transfers ownership of \lain{x} explicitly, and
\lain{return var x} returns a mutable borrow of \lain{x} (the pattern used by
a \lain{func} whose return type is \lain{var T}).  Ownership transfer is also
implicit from the function's declared return type, so a bare \lain{return x}
suffices when that type is owned.

\begin{constraint}
  A \lain{return var x} (or \lain{return mov x}) that would escape a borrow of a \emph{local}
  variable is \illformed{}~(\diagcode{E010}); returning a \lain{var} borrow tied to a
  \lain{var} parameter is permitted.  Returning is one of several ways a reference can outlive
  the storage it borrows, and the rule governing all of them is
  \S\,\ref{sec:mem.storage}.
\end{constraint}

\section{Defer statement}
\label{sec:stmt.defer}
\index{defer statement}

\pnum
\lain{defer} \textit{statement} schedules \textit{statement} for execution immediately
before the enclosing scope exits, on all exit paths (\lain{return},
\lain{break}, \lain{continue}, or fall-through).  Multiple \lain{defer}
statements execute in LIFO order.  The deferred construct is a single statement, not a braced
block: a block is not a statement here, so \lain{defer \{ ... \}} is \illformed{}.

\pnum
\textbf{Interaction with linear types}: if a linear variable is consumed
inside a \lain{defer} body, the variable is marked as defer-consumed.  It
is treated as unconsumed for the purposes of the main body (it may be used
before the scope exit) and as consumed at scope exit.

\pnum
A deferred statement is a scope of its own: a \lain{defer} inside it runs
when the deferred statement ends, as at the end of any block.

\begin{constraint}
  Control shall not leave a deferred statement: a \lain{return}, a
  \lain{break} or \lain{continue} aimed at a loop outside it, and a
  \lain{try} or \lain{else return} that leaves the function are
  \illformed{}~(\diagcode{E138}).  A loop inside the deferred statement may
  use \lain{break} and \lain{continue}.
\end{constraint}

\begin{example}
\begin{laincode}
import std.fs.{open_file, close_file}

func process() int effects io, raises, alloc {
    var f = open_file("data.txt", "r")
    defer close_file(mov f)       // f consumed at scope exit
    // ... use f ...
    return 0
}
\end{laincode}
\end{example}

\section{Assert and assume statements}
\label{sec:stmt.assert}
\index{assert statement}

\pnum
\lain{assert P} states a fact the compiler shall prove where it is written: its
predicate \lain{P}, an expression of type \lain{bool}, is a proof obligation, and a
predicate the analyses cannot discharge makes the program
\illformed{}~(\diagcode{E012}).  An \lain{assert} costs nothing at run time.
\lain{assume P} states a fact the compiler takes without proof, and is allowed only
inside an \lain{unsafe} block~(\diagcode{E129}).  Parentheses around the predicate
are optional, as for a module-scope \lain{assert}
(\S\,\ref{sec:decl.static-assert}).

\begin{note}
  The two are duals, and the asymmetry in where they are permitted follows from that.  An
  \lain{assert} \emph{adds} an obligation: the analyses must discharge it, so the worst a wrong
  one can do is refuse a program.  An \lain{assume} \emph{removes} one: it is believed, and every
  proof downstream of it is conditional on it being true.  An assumption nothing pays for is an
  axiom, and an axiom silently makes a prover able to prove a false statement --- which is why it
  is confined to \lain{unsafe}, where the programmer has already taken the obligation on.

  The practical use of \lain{assert} is to choose where imprecision is reported.  Without one, a
  fact the analyses fail to carry surfaces at whatever later line first needs it, often an array
  access several statements away; with one, it surfaces at the predicate that was actually lost.
\end{note}

\begin{example}
\begin{laincode}
func last(a u8[]) u8 {
    if a.len > 0 {
        n = a.len - 1
        assert n < a.len
        assert(n + 1 == a.len)
        return a[n]
    }
    return 0
}
\end{laincode}
\end{example}

\section{Comptime if statement}
\label{sec:stmt.comptime-if}
\index{comptime if}

\pnum
\lain{comptime if cond \{ then \} [else \{ else \}]} evaluates
\textit{cond} at compile time.  Only the taken branch is type-checked and
emitted; the other branch is discarded.  \textit{cond} shall be a
compile-time constant expression (\S\,\ref{sec:14-generics}).

\begin{note}
  \lain{comptime if} is the Lain equivalent of C preprocessor
  \texttt{\#if}: it enables platform-specific or type-specific code
  selection without dead-code warnings.
\end{note}

\section{For statement}
\label{sec:stmt.for}
\index{for statement}

\pnum
\lain{for i in start..end \{ body \}} iterates with \textit{i} ranging
from \textit{start} (inclusive) to \textit{end} (exclusive).  The loop
variable \textit{i} is immutable; its value range is statically known to
be $[\textit{start}, \textit{end}-1]$ throughout the body, enabling safe
array indexing without runtime bounds checks.

\pnum
\lain{for} loops are permitted whatever a function's row says: the range is the bound.

\begin{constraint}
  \textit{start} and \textit{end} shall have integer types.
\end{constraint}
