\chapter{Types}
\label{sec:07-types}
\index{type}

\pnum
Lain is statically typed.  Every variable, expression, and parameter has a
type determined at compile time.  There is no runtime type information
(RTTI).  The grammar productions for types are in Annex~A (\gramref{type}).

\section{Type taxonomy}
\label{sec:types.taxonomy}
\index{type!taxonomy}

\pnum
The types of Lain are organized as follows:

\begin{itemize}
  \item \textit{Primitive types}: integer, floating-point, boolean, void
        (\S\,\ref{sec:types.primitive});
  \item \textit{Array types}: fixed-size, compile-time-sized
        (\S\,\ref{sec:types.array});
  \item \textit{Slice types}: dynamically-sized views into contiguous memory,
        including sized slice types with static length constraints
        (\S\,\ref{sec:types.slice});
  \item \textit{Vector types}: a fixed number of lanes, operated on lane by lane
        (\S\,\ref{sec:types.vector});
  \item \textit{Struct types}: named product types (\S\,\ref{sec:types.struct});
  \item \textit{Enum types}: simple enumerations (\S\,\ref{sec:types.enum});
  \item \textit{ADT types}: sum types with associated data (\S\,\ref{sec:types.adt});
  \item \textit{Pointer types}: raw memory addresses, unsafe only
        (\S\,\ref{sec:types.pointer});
  \item \textit{Constrained types}: types with value range annotations
        (\S\,\ref{sec:types.constrained}).
\end{itemize}

\pnum
Types are classified as \textit{linear} or \textit{unrestricted}.  Linear
types must be consumed exactly once (see \S\,\ref{sec:11-ownership}).
Unrestricted types may be used any number of times.

\pnum
All primitive types are unrestricted.  A struct type is linear if and only
if at least one of its fields is of a linear type.  This property is
transitive.

\pnum
\lain{int} is a documented alias of \lain{i32}, identical in every
semantic respect (boundary checks, niche optimization, codegen). Use
either spelling — \lain{int} when bit-width is incidental, \lain{i32}
when explicit width matters.

\pnum
Generalized integer types \lain{iN}/\lain{uN} are admitted for any
$N \in [1, 64]$. Hardware-aligned widths
($N \in \{1, 8, 16, 32, 64\}$) map to standard C99 stdint types.
Logical widths (other $N$) occupy the smallest hardware-aligned
container that fits $N$ bits when standalone; in a \tok{[packed]}
struct they occupy exactly $N$ bits.

\pnum
\lain{usize} and \lain{isize} are the platform-native unsigned and signed
integer types whose width equals the pointer width.  Their exact width is
\idbehav{the pointer width on the target platform}.

\subsection{Hardware-aligned vs logical integer types}
\label{sec:types.iN-categories}
\index{integer type!hardware-aligned}
\index{integer type!logical}

\pnum
The \lain{iN}/\lain{uN} types fall into two semantic categories:

\textbf{Hardware-aligned} (\(N \in \{1, 2, 4, 8, 16, 32, 64\}\), with
the common subset being \(\{8, 16, 32, 64\}\)): these correspond to
fundamental C99 stdint widths (\texttt{uint8\_t}, \texttt{int32\_t},
etc.). They are the canonical choice for C interop and for any context
where exact storage size matters at the byte boundary.

\textbf{Logical} (other \(N\)): these are \textit{bit-width quantities}.
Their semantics are context-dependent:

\begin{itemize}
  \item \textbf{Standalone}: storage uses the smallest hardware-aligned
        container fitting \(N\) bits (e.g., \lain{u12} maps to
        \texttt{uint16\_t}). The natural range is
        \([-2^{N-1},\,2^{N-1}-1]\) signed or \([0,\,2^N-1]\) unsigned.
  \item \textbf{Inside a packed struct} (future feature,
        \S\,\ref{sec:types.packed-future}): the type occupies exactly
        \(N\) bits of storage with bit-exact layout.
\end{itemize}

\pnum
\textbf{Distinction from refinement.}  Logical \lain{iN}/\lain{uN} types
differ from a refinement constraint on \lain{int}:

\begin{itemize}
  \item \lain{int >= 0 and <= 7} declares an \lain{int} with a range
        constraint. Storage is the \lain{int} default (\texttt{int32\_t});
        bit-width is not specified.
  \item \lain{u3} declares a 3-bit quantity. Standalone its range is
        \([0, 7]\) and its storage is \texttt{uint8\_t}; in a
        \lain{[packed]} struct (\S\,\ref{sec:types.packed-future}) it occupies exactly 3 bits.
\end{itemize}

The two forms are interchangeable when only the range matters; they
differ when bit-exact storage layout matters.

\begin{example}
\begin{laincode}
// A refinement constraint on int, named: range [0, 4095], container = int32_t.
// (A constraint is written on a parameter, a field or an alias like this one,
// not on a local's declaration.)
type Twelve = int >= 0 and <= 4095
type Pressure = int >= 0 and <= 1000

func main() int {
    var x u12 = 4095        // logical bit-width: a 12-bit quantity, container = uint16_t
    var y Twelve = 4095     // the same range as an int refinement
    var p Pressure = 500
    return 0
}
\end{laincode}
\end{example}

\subsection{Refinement type aliases}
\label{sec:types.alias-refinement}
\index{refinement type}
\index{type alias!refinement}

\pnum
A type alias may carry a refinement constraint that narrows the underlying
type's value range:

\begin{laincode}
type Percent = int >= 0 and <= 100
type Pressure = int >= 0 and <= 1000
type NonZero = int != 0
\end{laincode}

\pnum
Variables declared with a refinement type alias inherit its constraint.
Assignments whose source value range violates the alias constraint are
\illformed{}~(\diagcode{E086}).

\begin{example}
\begin{laincode}
type Percent = int >= 0 and <= 100

func main() int {
    var ok Percent = 75              // accepted: 75 fits [0, 100]
    // var bad Percent = 150         // refused, E086: 150 > 100
    return 0
}
\end{laincode}
\end{example}

\subsection{Packed structs}
\label{sec:types.packed-future}
\index{packed struct}
\index{bitfield}

\pnum
The \tok{[packed]} attribute (\S\,\ref{sec:decl.attributes}) on a struct
declaration enables bit-exact memory layout. Each \lain{iN}/\lain{uN}
field occupies exactly \(N\) bits within a single scalar container.

\begin{laincode}
[packed]
type GpioModer {
    pin0 u2     // bit 0-1
    pin1 u2     // bit 2-3
    pin2 u2     // bit 4-5
    pin3 u2     // bit 6-7
}
// total: 8 bits -> uint8_t container, bit-exact layout
\end{laincode}

\pnum
\textbf{Layout rules}:
\begin{itemize}
  \item Fields are laid out in declaration order, starting at bit 0.
  \item Each field occupies exactly its declared bit width.
  \item Total bit width must be \(\leq 64\); container is the smallest
        of \texttt{uint8\_t}, \texttt{uint16\_t}, \texttt{uint32\_t}, or
        \texttt{uint64\_t} that fits the total.
\end{itemize}

\pnum
\textbf{Access semantics}:
\begin{itemize}
  \item Construction: \lain{GpioModer(1, 2, 3, 0)} packs the four
        2-bit fields into the container.
  \item Read: \lain{r.pin1} extracts bits 2-3 via shift-and-mask; an \lain{iN} field is
        sign-extended.
  \item Write: \lain{r.pin1 = v} updates bits 2-3, leaving other
        fields unchanged.
  \item The whole struct is the container integer: it is copied, passed and returned as one.
\end{itemize}

\begin{constraint}
  Inside a \tok{[packed]} struct, fields shall be \lain{iN}/\lain{uN}
  types only. Nested structs, pointers, and slices are not permitted.
  Violation is \illformed{}~(\diagcode{E121}).
\end{constraint}

\begin{constraint}
  The total bit width of fields in a \tok{[packed]} struct shall not
  exceed 64. Otherwise \illformed{}~(\diagcode{E121}).
\end{constraint}

\begin{constraint}
  A field of a \tok{[packed]} struct has no address. A \lain{var} reference to one
  (\lain{f(var r.pin1)}, \lain{var x = var r.pin1}) or its address (\lain{\&r.pin1}) is
  \illformed{}~(\diagcode{E121}), inside \lain{unsafe} as well: this is a property of the
  representation, not a safety policy. A \lain{var} reference to the whole struct is well-formed.
\end{constraint}

\begin{note}
  This feature targets embedded use cases: hardware registers,
  packed network protocols, codec implementations. The reference
  implementation emits the container as a scalar typedef and every access inline:
  shift-and-mask reads, read-modify-write stores, and construction by OR-ing the shifted
  fields. The layout can be asserted where the type is declared:
  \lain{assert @sizeof(GpioModer) == 1} (\S\,\ref{sec:decl.static-assert}).
\end{note}

\subsection{Integer rank and widening}
\label{sec:types.rank}
\index{integer rank}
\index{integer widening}

\pnum
The integer types are partially ordered by \textit{rank}:

\begin{longtable}{@{}lll@{}}
\toprule
\textbf{Rank} & \textbf{Types} & \textbf{Bit width} \\
\midrule
\endfirsthead
\toprule
\textbf{Rank} & \textbf{Types} & \textbf{Bit width} \\
\midrule
\endhead
\bottomrule
\endlastfoot
1 & \lain{u8}, \lain{i8}             & 8 \\
2 & \lain{u16}, \lain{i16}           & 16 \\
3 & \lain{u32}, \lain{i32}, \lain{int} & 32 \\
4 & \lain{u64}, \lain{i64}           & 64 \\
5 & \lain{usize}, \lain{isize}       & platform \\
\end{longtable}

\pnum
\textbf{Implicit widening}: a value of a lower-rank integer type may be
used where a higher-rank integer type is expected, without an explicit cast.

\pnum
\textbf{Result type of arithmetic (auto-widening)}.  The result type of a plain
\lain{+}, \lain{-}, or \lain{*} is \emph{wide enough to hold every representable
result}, so the operation itself cannot overflow: \lain{+}/\lain{-} widen by one
bit (with a sign bit when an unsigned operand feeds a signed result) and \lain{*}
sums the operand widths --- e.g. \lain{u8 + u8} yields \lain{u9}, \lain{u8 - u8}
yields \lain{i10}, \lain{i32 + i32} yields \lain{i33}, and \lain{i32 * i32} yields
\lain{i64}.  When the required width would exceed 64 bits (the \lain{i128}
ceiling), the result type is the higher-rank operand and the operation is subject
to the overflow diagnostic below.  A \emph{signed} \lain{/} widens by one bit ---
\lain{i32 / i32} yields \lain{i33} --- because exactly one quotient does not fit its
operands' type, \(\mathrm{TYPE\_MIN} / {-1}\); an unsigned \lain{/} and every
\lain{\%} keep the higher-rank operand type (a remainder is smaller in magnitude than its
divisor).  The other binary operators (\lain{\&}, \lain{|}, \lain{\^}, \lain{<<},
\lain{>>}) yield the higher-rank operand type.  Overflow therefore becomes possible only
at a \emph{narrowing} (\S\,\ref{sec:types.overflow}).

\begin{example}
\begin{laincode}
var a u8  = 42
var b int = a          // u8 -> int: implicit widening, OK
var c = a + a          // u8 + u8 -> u9 (holds 0..510; cannot overflow)
var d = c as u8        // narrowing back to u8 is checked (see below)
\end{laincode}
\end{example}

\begin{constraint}
  An implicit conversion from an integer type to one that cannot represent every
  value of the source --- a narrowing, or a signedness change --- is
  \illformed{}\ unless value-range analysis proves it fits
  (\S\,\ref{sec:13-vra}).  Such a conversion otherwise requires an explicit cast
  tier (\lain{as}, \lain{as?}, \lain{as\%}, or \lain{as|};
  \S\,\ref{sec:expr.cast}).
\end{constraint}

\subsection{Integer overflow}
\label{sec:types.overflow}
\index{integer overflow}

\pnum
Because \lain{+}, \lain{-}, and \lain{*} auto-widen (\S\,\ref{sec:types.rank}),
overflow cannot occur at the operation.  It can occur only when a value flows
into a type that cannot hold it --- a \emph{narrowing} at an assignment, return,
argument, or explicit cast.  A narrowing whose value range is not proven to fit
the target is \illformed{}~(\diagcode{E086}); the programmer resolves it by
proving the range, widening the target, or choosing an explicit overflow policy:

\begin{longtable}{@{}ll@{}}
\toprule
\textbf{Policy} & \textbf{Form} \\
\midrule
\endhead
\bottomrule
\endlastfoot
proven (default)     & \lain{x as T}\quad(narrows only if proven, else \diagcode{E086}) \\
checked (\lain{else}) & \lain{x as? T},\quad \lain{a +? b}, \lain{a -? b}, \lain{a *? b} \\
wrapping (modular)   & \lain{x as\% T},\quad \lain{a +\% b}, \lain{a -\% b}, \lain{a *\% b}, \lain{a /\% b} \\
saturating (clamp)   & \lain{x as| T},\quad \lain{a +| b}, \lain{a -| b}, \lain{a *| b}, \lain{a /| b} \\
\end{longtable}

\pnum
A checked form performs a run-time test and, on overflow, evaluates its \lain{else} arm ---
a fallback value, a \lain{return}, or \lain{panic(...)}, which terminates the program; a
checked form without \lain{else} is \illformed{}~(\diagcode{E067}).  A wrapping form uses
two's-complement modular arithmetic.  A saturating form clamps to the target type's minimum or
maximum.  Every form is defined at every integer width, odd widths included: a wrapping result
is reduced modulo \(2^N\) for the type's own \(N\), not for the width of the machine type that
holds it.
The checked, wrapping and saturating \emph{operators} compute in one integer type, chosen from
their operands and never wider than the wider stated one:
\begin{itemize}
  \item an integer literal, negated or not, and plain arithmetic (\lain{+}, \lain{-}, \lain{*},
        \lain{/}, whose type the compiler widened so that it cannot overflow) take the other
        operand's type, on either side, and the policy applies to their exact value:
        \lain{100 +\% x} is \lain{x +\% 100}, and \lain{s +\% x * y} over \lain{i32}s wraps in
        \lain{i32}.  The exact value is not the same as the value reduced to the chosen type
        first, and the difference is observable wherever a literal does not fit it: on a
        \lain{u8}, \lain{x +| 300} saturates the exact 310 and yields 255, where reducing 300 to
        a \lain{u8} first would yield 54.  For \lain{+\%} the two readings coincide --- both
        yield 54 --- so a reader who assumes the reduction is wrong only about saturation, and
        only sometimes;
  \item of two stated types that differ, the one that holds every value of the other, in either
        order: \lain{a +| b} and \lain{b +| a} with a \lain{u8} and a \lain{u32} are both a
        \lain{u32} saturating add;
  \item two stated types neither of which holds every value of the other (\lain{u32} and
        \lain{i32}, \lain{i32} and \lain{u64}) are \illformed{}~(\diagcode{E012}): convert one.
\end{itemize}
\begin{laincode}
// VERIFY: exit 255
func sat(x u8) u8 { return x +| 300 }      // the exact 310, clamped
func wrap(x u8) u8 { return x +% 300 }     // 310 mod 256

func main() i32 {
    if wrap(10) as i32 != 54 { return 1 }
    return sat(10) as i32
}
\end{laincode}

The amount of a wrapping shift \lain{x <<\% k} is a count, not an operand, and may have any
integer type.  For division the only overflowing case is
\(\mathrm{TYPE\_MIN} / {-1}\): \lain{/\%} yields \(\mathrm{TYPE\_MIN}\) and \lain{/|}
yields \(\mathrm{TYPE\_MAX}\); every other quotient is the ordinary one.

\begin{constraint}
  Where no wider type exists --- a signed \lain{/} or \lain{\%} on 64-bit operands --- the
  operation itself must be proven not to divide \(\mathrm{TYPE\_MIN}\) by \({-1}\): the
  dividend's range excludes \(\mathrm{TYPE\_MIN}\) or the divisor's excludes \({-1}\).
  Otherwise the program is \illformed{}~(\diagcode{E086}).  There is no implicit run-time
  check; \lain{/\%} and \lain{/|} state what the programmer means.
\end{constraint}

\begin{constraint}
  An implicit conversion between integer types and floating-point types is
  \illformed{}.  Such conversions require an explicit \lain{as} cast.
\end{constraint}

\begin{constraint}
  An implicit conversion between integer types and \lain{bool} is
  \illformed{}.  Such conversions require an explicit \lain{as} cast.
\end{constraint}

\subsection{Floating-point types}
\label{sec:types.float}
\index{floating-point type}

\pnum
\lain{f32} and \lain{f64} are 32-bit and 64-bit floating-point types
conforming to IEC~60559 (IEEE~754).  They correspond to C's \texttt{float}
and \texttt{double} respectively.  \lain{float} is a documented alias
of \lain{f32}.

\pnum
The default type of a floating-point literal is \lain{f64}
(\S\,\ref{sec:lex.literals.float}).

\pnum
Arithmetic on \lain{f32} and \lain{f64} follows IEEE~754 semantics:
overflow produces $\pm\infty$; the result of $0.0/0.0$ and similar
operations is NaN.  These are defined behaviors in Lain.

\subsection{Boolean type}
\label{sec:types.bool}
\index{boolean type}

\pnum
\lain{bool} has exactly two values: \lain{true} and \lain{false}.  Every boolean the language
makes has this type: the literals, the comparisons, \lain{in}, and \lain{and}, \lain{or} and
\lain{!} (\S\,\ref{sec:expr.logical}); none of them is an integer.
\lain{bool} is stored as a single byte; its exact representation is
\idbehav{whether \lain{true} is 1 or any non-zero value}.

\begin{constraint}
  There are no implicit \textbf{value} conversions between \lain{bool}
  and any integer type for general arithmetic or assignment.
\end{constraint}

\pnum
The condition expression of \lain{if} and \lain{while} accepts either
a value of type \lain{bool} or any integer type.  When an integer
value is used in condition position, zero is treated as \lain{false}
and any non-zero value is treated as \lain{true}.  This relaxation is
ergonomic only and does not extend to other contexts.

\begin{example}
\begin{laincode}
var n int = read_count()
if n { ... }        // OK: integer in condition, non-zero is true
var b bool = n      // [E012]: not a value conversion; write n != 0
\end{laincode}
\end{example}

\subsection{The void type}
\label{sec:types.void}
\index{void type}

\pnum
\lain{void} represents the absence of a value.  It is used exclusively
in pointer types (\lain{*void}) for C interoperability (see
\S\,\ref{sec:17-interop}).

\begin{constraint}
  A variable, parameter or field of type \lain{void} is
  \illformed{}~(\diagcode{E012}).
\end{constraint}

\section{Array types}
\label{sec:types.array}
\index{array type}

\pnum
An array type \lain{T[N]} denotes a contiguous sequence of $N$ values of
type~\lain{T}.  $N$ shall be a compile-time constant integer greater than
zero (grammar: \gramref{array-type}).

\pnum
The \texttt{.len} property of an array type yields $N$ as a compile-time
constant of type \lain{int}.

\pnum
In a local declaration, \lain{N} may be any constant expression, a module constant
(\lain{var a u8[K]}) as well as a literal; the local is then a fixed array of \lain{N}
elements, and an initializer shall have exactly that length (\diagcode{E012}). A length that is
not a constant expression is \illformed{} in a declaration with an initializer
(\diagcode{E137}): without one, the local is a VLA (the note below). A type alias may name an
array type, \lain{type Buf4 = u8[K]}, and is that array type.

\begin{note}
  \textbf{Runtime-length local arrays (VLAs).}  A \emph{local} declaration
  \lain{var a T[n]} whose length \lain{n} is a runtime value and which has no
  initializer is an owned, runtime-sized stack array (emitted as a C
  variable-length array \texttt{T a[n]}), with \lain{a.len == n} and native
  bounds-checked indexing.  It is distinct from a sized-slice \emph{view} of the
  same spelling: a parameter \lain{f(a T[n])}, or an \emph{initialized} local
  \lain{var s = arr[i..j]}, is a borrowed \lain{\{len, data\}} slice, not owned
  storage.  Indexing a VLA under a proven guard (\lain{i < n}) needs no
  \lain{unsafe}; an index VRA cannot bound is \diagcode{E085} as for any array.
\end{note}

\pnum
Array elements are laid out contiguously in memory in increasing index
order, with element~0 at the base address.  The stride between elements is
\idbehav{equal to \texttt{sizeof(T)} in C99, including any intra-element
padding}.

\begin{constraint}
  An array size $N \leq 0$ is \illformed{}~(\diagcode{E100}).
\end{constraint}

\begin{constraint}
  Every array index expression shall satisfy
  $0 \leq \textit{idx} < \textit{arr.len}$.
  An access for which value range analysis cannot prove this is an
  out-of-bounds violation~(\diagcode{E085}).
\end{constraint}

\begin{example}
\begin{laincode}
var arr int[5] = [1, 2, 3, 4, 5]
var x = arr[2]         // OK: 2 is statically in [0, 4]
// var y = arr[5]      // [E085]: 5 >= arr.len
\end{laincode}
\end{example}

\section{Slice types}
\label{sec:types.slice}
\index{slice type}

\pnum
A slice type \lain{T[]} is a reference to a contiguous sequence of values
of type~\lain{T} whose length is determined at runtime.  Its runtime
representation is a \textit{fat} pair \texttt{(len: usize, data: *T)} --- a
length followed by a data pointer.

\begin{constraint}
  \textbf{The \lain{*} rule.}  A \lain{*} prefix denotes a \emph{raw pointer},
  and only that.  Arrays and slices are always passed by reference, so they
  never carry a \lain{*}: a slice is \lain{T[]}, a sized slice \lain{T[n]}, a
  fixed array \lain{T[N]}, a sentinel string \lain{T[:S]}.  A \lain{*} is
  permitted only before a non-array, non-slice type --- \lain{*T}, \lain{**T},
  \lain{*void}, and function-pointer types (\S\,\ref{sec:17-interop}).  A
  \lain{*} before any bracket form is \illformed{}~(\diagcode{E100}).
\end{constraint}

\pnum
The reference/pointer type family and its C mapping (parameter position):

\begin{center}
\begin{tabular}{@{}llll@{}}
\toprule
\textbf{Lain} & \textbf{What it is} & \textbf{C parameter} & \textbf{Cost} \\
\midrule
\lain{u8}     & scalar             & \texttt{uint8\_t} (by value)       & 1 word \\
\lain{T[N]}   & inline fixed array & \texttt{const Fixed\_T\_N*}        & N$\times$sizeof(T) \\
\lain{T[]}    & fat slice          & \texttt{size\_t \_\_len, const T*} & 2 words \\
\lain{T[n]}   & sized slice        & \texttt{size\_t, const T*}         & 2 words \\
\lain{T[:S]}  & sentinel string    & \texttt{struct \{ T* data; \}}     & 1 word \\
\lain{*T}     & raw pointer        & \texttt{const T*}                  & 1 word \\
\lain{*void}  & opaque C pointer   & \texttt{const void*}               & 1 word \\
\bottomrule
\end{tabular}
\end{center}

\begin{note}
  A \lain{*} in the emitted C has \emph{two} independent sources: (1) a \lain{*}
  written in the Lain type, which is a raw pointer; and (2) the implicit
  by-reference passing of an \emph{aggregate} (array, slice, struct) parameter
  --- a hidden \texttt{const T*} that is part of the calling convention, not the
  type.  The same aggregate is a plain value as a local (\lain{var p Point}
  emits \texttt{Point p}) but a pointer as a parameter (\texttt{const Point*}).
  This is why an aggregate type carries no \lain{*} even though it is passed as a
  pointer: the \lain{*} names raw pointers, not the borrow.
\end{note}

\pnum
A slice has two properties accessible via dot notation:
\begin{itemize}
  \item \texttt{.len}: the number of elements, type \lain{usize};
  \item \texttt{.data}: a pointer to the first element, type \lain{*T}.
\end{itemize}

\pnum
A string literal of $N$ characters has static type \lain{Fixed\_u8\_{N+1}}
(a null-terminated fixed-size array of $N{+}1$ bytes) and is implicitly
coercible to \lain{u8[]}.

\subsection{Sized slice types}
\label{sec:types.sized-slice}
\index{sized slice type}
\index{slice type!sized}

\pnum
A \textit{sized slice type} is a slice type annotated with a size constraint
on its length.  The constraint is part of the parameter or variable
declaration, not of the nominal type itself.  The syntax is:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Syntax} & \textbf{Meaning} \\
\midrule
\lain{T[]}          & unsized dynamic slice (no length constraint) \\
\lain{T[n]}         & length exactly \lain{n}; \textit{n} is a size expression \\
\lain{T[>= n]}      & length $\geq$ \lain{n}; \textit{n} is a size expression \\
\lain{T[> n]}       & length $>$ \lain{n}; \textit{n} is a size expression \\
\bottomrule
\end{tabular}
\end{center}

\pnum
A \textit{size expression} (\textit{size\_expr}) may be any of:

\begin{itemize}
  \item an integer literal (e.g., \lain{3}, \lain{0});
  \item an identifier that names a numeric variable in scope (e.g., \lain{n});
  \item a member expression of the form \lain{p.len}, where \lain{p} is a
        slice or array parameter in scope (e.g., \lain{a.len}, \lain{src.len});
  \item a binary arithmetic expression over the above
        (e.g., \lain{a.len + b.len}, \lain{src.len - 1}).
\end{itemize}

\begin{example}
\begin{laincode}
// Exact-length constraint: out must have length == a.len + b.len
// (the bounds keep a.len + b.len from overflowing a usize)
func concat(a i32[<= 1000000], b i32[<= 1000000], out i32[a.len + b.len]) {
    for j in 0..a.len { out[j] = a[j] }
    for j in 0..b.len { out[j + a.len] = b[j] }
}

// Lower-bound constraint: arr must have at least one element
func first(arr i32[> 0]) i32 { return arr[0] }

// Derived constraint using member .len (src is not empty, so src.len - 1 cannot underflow)
func slide(src i32[>= 1], out i32[src.len - 1]) {
    for i in 0..out.len { out[i] = src[i + 1] -% src[i] }
}
\end{laincode}
\end{example}

\pnum
\textbf{Constraint semantics.}
\begin{itemize}
  \item \lain{T[expr]}: the value range analysis (VRA, \S\,\ref{sec:13-vra})
        records the constraint \texttt{len == expr} and uses it to prove
        subsequent bounds checks inside the function body.
  \item \lain{T[>= expr]}: VRA records \texttt{len >= expr}.
  \item \lain{T[> expr]}: VRA records \texttt{len > expr}, i.e.\ \texttt{len >= expr + 1}.
\end{itemize}

\pnum
\textbf{Call-site verification.}
At every call site, the compiler verifies that the argument satisfies the
formal parameter's size constraint (\diagcode{E087}); see
\S\,\ref{sec:vra.sized-slice-callsite}.

\pnum
\textbf{C ABI decomposition (Fase~7).}
When a function parameter has a sized or unsized dynamic slice type, the
compiler decomposes it into a pair of C parameters:

\begin{itemize}
  \item a length parameter \texttt{size\_t};
  \item a data pointer \texttt{T* restrict}.
\end{itemize}

Whether the callee may write through the pointer is stated by the GCC attribute
\texttt{access(read\_only, $p$, $n$)} or \texttt{access(read\_write, $p$, $n$)}, where $p$ and
$n$ are the positions of the pointer and its length. A slice whose length is an expression over
other parameters' lengths (\lain{out i32[a.len + b.len]}) is passed the same way: its length is
an ordinary parameter, checked against the expression at every call
(\S\,\ref{sec:vra.sized-slice-callsite}).

\begin{example}
\begin{laincode}
// Source:
func vadd(var out i32[], a i32[out.len], b i32[out.len]) {
    for i in 0..out.len { out[i] = a[i] +% b[i] }
}

// C emission (the name is prefixed with its module's):
// __attribute__((access(read_write, 2, 1))) __attribute__((access(read_only, 4, 3)))
// __attribute__((access(read_only, 6, 5)))
// void vadd(size_t, int32_t* restrict, size_t, int32_t* restrict,
//           size_t, int32_t* restrict);
\end{laincode}
\end{example}

\section{Vector types}
\label{sec:types.vector}
\index{type!vector}\index{SIMD}

\pnum
\lain{Vec(N, T)} is a value of \lain{N} \emph{lanes} of type \lain{T}, held and passed whole.
\lain{T}x\lain{N} is the same type: \lain{u8x16} is \lain{Vec(16, u8)}, \lain{i32x4} is
\lain{Vec(4, i32)}. A vector may be a local, a parameter, a return value or a struct field.

\begin{constraint}
  \lain{N} shall be a power of two from 1 to 64, and \lain{T} an 8, 16, 32 or 64-bit integer
  type, or \lain{f32} or \lain{f64} (\diagcode{E100}).
\end{constraint}

\pnum
A vector is built from an array literal of exactly \lain{N} elements where a vector is
expected: a declaration, an argument, a field, a return, or an operand beside a vector
(\lain{a - [1, 1, 1, 1]}). \lain{@splat(V, x)} is the vector of type \lain{V} with \lain{x} in
every lane.

\pnum
The arithmetic, bitwise and shift operators and the comparisons apply lane by lane, and a
scalar operand applies to every lane. Integer lanes \emph{wrap}: a lane's result is taken modulo
$2^w$ for a $w$-bit lane, including unary \lain{-}, so vector arithmetic carries no overflow
obligation. Two obligations remain, as on scalars:
\begin{itemize}
  \item a division or remainder's divisor shall be provably non-zero (\diagcode{E015}); a
        scalar divisor is judged like a scalar's, while a vector divisor cannot be proven,
        because the analysis holds no per-lane facts;
  \item a shift's amount shall be a scalar provably in $[0, w-1]$ (\diagcode{E086}); an amount
        given per lane is refused for the same reason.
\end{itemize}

\pnum
A comparison yields a \emph{mask}: every bit of a lane is set where the comparison holds and
clear where it does not (255 and 0 for \lain{u8} lanes). For integer lanes the mask has the
operands' vector type; for \lain{f32} and \lain{f64} lanes it has \lain{i32} and \lain{i64}
lanes, so a lane that held is $-1$ (a float with every bit set would be a NaN, not a mask).

\pnum
\lain{v[k]} is lane \lain{k} of \lain{v}, read or written in place. \lain{k} shall be provably
less than \lain{N} (\diagcode{E085}).

\pnum
\lain{@load(V, b, i)} reads the \lain{N} elements of \lain{b} starting at element \lain{i} into
a vector of type \lain{V}, and \lain{@store(b, i, v)} writes \lain{v}'s lanes there. For an
array or slice \lain{b} the obligation is \lain{i + N <= b.len} (\diagcode{E085}). A raw pointer
has no length, so a load or store through one is allowed only inside \lain{unsafe}. \lain{b}
shall be an array, a slice or a raw pointer (\diagcode{E100}): a struct's bytes are in an order
the implementation chooses (\S\,\ref{sec:types.struct}).

\pnum
\lain{@movemask(v)} is the \lain{u32} whose bit \lain{k} is the top bit of lane \lain{k}: of a
mask, the lanes where the comparison held.

\begin{constraint}
  The operand of \lain{@movemask} shall be a vector of at most 32 lanes of 8 bits
  (\diagcode{E100}).
\end{constraint}

\pnum
\lain{@popcount(x)}, \lain{@ctz(x)} and \lain{@clz(x)} take an integer and give a \lain{u32}:
the number of bits of \lain{x} that are set, the number of zero bits below its lowest set bit,
and the number above its highest, counted in \lain{x}'s width. With \lain{@movemask} they scan a
mask: \lain{@ctz} of a mask is its first matching lane.

\begin{constraint}
  The argument of \lain{@ctz} and of \lain{@clz} shall be provably non-zero, as a divisor shall:
  from its type, its range or a guard (\diagcode{E015}). Neither count is defined for 0, which
  is the mask of a comparison that matched no lane.
\end{constraint}

\begin{laincode}
func first_match(bits u32) u32 {
    if bits == 0 { return 32 }      // no lane matched
    return @ctz(bits)
}
\end{laincode}

\pnum
\lain{@shuffle(t, idx)} is a table lookup: lane \lain{k} of the result is
\lain{t[idx[k]]} when \lain{idx[k] < N}, and 0 otherwise. It is total: an index out of range
reads 0, never another lane and never an undefined value, so it states no obligation. This is
the behaviour of ARM NEON's \texttt{tbl} and of Rust's \texttt{swizzle\_dyn}; on x86 with SSSE3
it is \texttt{pshufb}. The classifier idiom \lain{@shuffle(tbl, (x >> 4) & 15)} indexes a
16-entry table by each byte's high nibble.

\begin{constraint}
  \lain{t} shall be a vector of integer lanes and \lain{idx} a vector of as many lanes of the
  unsigned integer type of the same width: \lain{u8x16} for a \lain{u8x16} or \lain{i8x16}
  table, \lain{u32x4} for a \lain{u32x4} table (\diagcode{E100}).
\end{constraint}

\pnum
The language names no instruction set. A vector is translated to a C \texttt{vector\_size}
type; the C compiler's target flags choose the instructions, and the same program builds for
x86-64 and AArch64. \lain{@movemask} uses the SSE2 or AVX2 intrinsic where the target defines
it and a portable loop elsewhere; \lain{@shuffle} uses \texttt{\_\_builtin\_shuffle} under GCC
and a lane loop elsewhere.

\section{Struct types}
\label{sec:types.struct}
\index{struct type}

\pnum
A struct type groups named fields into a single named product type.  The
grammar production is \gramref{struct-declaration} (Annex~A).

\pnum
A struct's fields are constructed and accessed by name; the order in which they are
\emph{stored} is the implementation's. It stores them by decreasing alignment, fields of equal
alignment in declaration order, so that the padding between them is the least the alignments
allow. The memory layout is then \idbehav{the C99 layout of the fields in that order, including
compiler-inserted padding for alignment}.

\begin{laincode}
type TokenKind { Ident, Number, Punct }
type Token {
    kind TokenKind      // one byte, stored last
    pos  u32
    len  u16
}
assert @sizeof(Token) == 8     // 12 in declaration order
\end{laincode}

\pnum
A struct whose layout is read outside the program keeps its declaration order:
\begin{itemize}
  \item one declared \tok{[ordered]} (\S\,\ref{sec:decl.attributes}) --- a file format, a wire
        header;
  \item one declared \tok{[packed]} (\S\,\ref{sec:types.packed-future}), whose bit order is the
        declaration;
  \item one reachable from the signature of an \lain{extern} function --- by value, or through a
        pointer, an array, a slice, a vector, a function pointer or a field of such a struct ---
        since the foreign code was written against the declaration.
\end{itemize}
A tagged sum's payloads (\S\,\ref{sec:types.adt}) are stored the same way, each by decreasing
alignment, unless the sum is declared \tok{[ordered]} or is reachable from an \lain{extern}
signature; either keeps every payload in declaration order.
Inside a program the storage order is not observable: there are no stored references, field
addresses cannot be compared or converted to integers, \lain{@load} and \lain{@store} take
an array, a slice or a raw pointer, never a struct (\S\,\ref{sec:types.vector}), and a cast that
would view a reorderable struct's bytes is refused (below). Only the size is observable, through
\lain{@sizeof}.

\begin{constraint}
  A cast between a pointer to a struct whose storage order the compiler chooses --- one not
  declared \tok{[ordered]} or \tok{[packed]}, not reachable from an \lain{extern} signature, and
  of more than one field --- and any other type (another pointer, an integer) is
  \illformed{}~(\diagcode{E012}), in either direction and inside \lain{unsafe} as well:
  \lain{unsafe} permits the cast, not an unspecified layout. So is such a cast over an array of
  that struct, or over a struct that holds it by value. Viewing a struct's bytes needs a declared
  layout: \tok{[ordered]}. A cast between pointers to the same struct type is not a view.
  The same holds for a tagged sum with a payload of more than one field whose order the
  compiler chooses: viewing its bytes needs \tok{[ordered]} on the sum. A sum whose payloads
  have at most one field each has no order to expose.
\end{constraint}

\pnum
A struct type~$S$ is linear if at least one field of $S$ has a linear type
(transitively).

\begin{constraint}
  \textbf{Q-008.}
  Every field of a struct or enum variant whose declared type is linear
  shall be annotated \lain{mov}.  Omitting \lain{mov} on a linear field
  is \illformed{}~(\diagcode{E083}).  This requirement makes linearity
  locally visible in the declaration: a reader of a struct definition
  does not need to inspect the field's type definition to know whether
  the struct is linear.
\end{constraint}

\begin{example}
\begin{laincode}
type Handle {
    mov ptr *int            // explicit `mov` on linear field
}

type Session {
    mov h Handle            // OK: Handle is linear, mov required
    name u8[]               // unrestricted field, no mov needed
}

// Ill-formed: missing mov on a linear field
type Bad {
    h Handle                // [E083]
}
\end{laincode}
\end{example}

\pnum
\textbf{Struct construction}: all fields shall be provided in declaration
order.  The type of each argument shall be compatible with the declared
field type (\S\,\ref{sec:types.compat}).

\begin{constraint}
  A struct constructor expression with a number of arguments different from
  the number of fields is \illformed{}~(\diagcode{E100}).
\end{constraint}

\begin{constraint}
  Writing to a field of a struct variable requires the variable to be
  declared as \lain{var} (mutable).  Writing to an immutable binding's
  field is \illformed{}.
\end{constraint}

\begin{constraint}
  Using \lain{==} or \lain{!=} on a struct type is \illformed{}.
  Field-by-field comparison must be performed explicitly.
\end{constraint}

\subsection{Field invariants}
\label{sec:types.struct.invariants}
\index{field invariant}
\index{struct invariant}

\pnum
A field declaration may state a fact about the field's value for the whole life of every value
of the struct type. Three forms are provided:
\begin{itemize}
  \item \lain{pos usize in text} --- an \emph{index} invariant: \lain{pos} is a valid index into
        the slice or array field \lain{text} (\lain{pos < text.len});
  \item \lain{pos usize <= src.len} --- a \emph{position} invariant: \lain{pos} compared with the
        length of the slice or array field \lain{src}, by \lain{<}, \lain{<=}, \lain{>} or
        \lain{>=};
  \item \lain{len usize <= cap} --- a relation between two integer fields, by the same four
        comparisons;
  \item \lain{src u8[<= 4294967295]} --- a \emph{length bound} on a slice field: its length
        compared with an integer constant, written inside the brackets as for a parameter
        (\lain{a i32[>= 2]}), by \lain{<}, \lain{<=}, \lain{>}, \lain{>=} or \lain{==}. The
        constant may be a literal, a module constant (\lain{src u8[<= MAXU32]}) or an
        expression over them (\lain{src u8[<= (1 << 32) - 1]}), evaluated as a module-scope
        \lain{assert} is (\S\,\ref{sec:decl.static-assert}); it is enforced exactly as the
        literal it evaluates to. A fixed-length field may be sized the same way:
        \lain{data u8[BUF]} is \lain{data u8[64]} when \lain{BUF} is 64.
\end{itemize}
A refinement against a literal (\lain{pct i32 <= 100}) is a plain field refinement
(\S\,\ref{sec:types.constrained}) and is not a field invariant.

\pnum
A length bound is what a \emph{narrow} position needs: \lain{pos u32 <= src.len} does not make
\lain{pos + 1} fit a \lain{u32} when \lain{src.len} is a \lain{usize}, since a longer source admits
\lain{pos} \(= 2^{32}-1\); bounding \lain{src} to at most \(2^{32}-1\) bytes does. A slice field's
length changes only when the field (or the whole struct) is written --- a \lain{var} reference
cannot rebind a slice (\diagcode{E009}) and an element write keeps the length --- so those writes
are where it is checked.

\pnum
An index invariant cannot hold for an empty container. A position invariant can:
\lain{pos usize <= src.len} admits \lain{pos == 0} over an empty source and
\lain{pos == src.len} at its end, which is the state a scanner is in at end of input.

\begin{constraint}
  A field invariant shall hold wherever a value of the struct type is built, and after every
  write to either field it relates. A construction or a field write at which it is not proven is
  \illformed{}~(\diagcode{E121}).
\end{constraint}

\begin{constraint}
  A \lain{var} reference to a field that a field invariant relates --- a \lain{var} argument
  (\lain{f(var s.pos)}) or a reference binding (\lain{var r = var s.pos}) --- is
  \illformed{}~(\diagcode{E121}): a write through it would not be checked against the invariant.
  Pass the whole struct as \lain{var} instead; writes to its fields are checked.
\end{constraint}

\begin{constraint}
  A field refinement naming another field in any other shape --- another comparison, a field of
  another kind, an expression --- is \illformed{}~(\diagcode{E132}).  So is a field whose length
  is bounded or sized by anything but a constant (other than the struct's own generic parameter,
  \lain{type Buf(N usize) \{ data u8[N] \}}), and a refinement written after a slice type
  (\lain{src u8[] <= 4096}), which bounds nothing a slice has.
\end{constraint}

\pnum
Because every write that could break a field invariant is checked, the invariant is a fact at
every read of the field: \lain{c.text[c.pos]} needs no bounds check under
\lain{pos usize in text}, and \lain{b.cap - b.len} needs no underflow check under
\lain{len usize <= cap}.

\begin{example}
\begin{laincode}
type Lexer {
    src u8[]
    pos usize <= src.len         // position: 0 <= pos <= src.len
}
func lexer_new(text u8[:0]) Lexer { return Lexer(text, 0) }   // OK even for ""
func advance(l var Lexer) {
    if l.pos < l.src.len { l.pos = l.pos + 1 }                 // keeps the invariant
}
\end{laincode}
\begin{laincode}
type Lexer {
    src u8[]
    pos usize <= src.len
}
func bad(l var Lexer) { l.pos = l.pos + 1 }   // ERROR: E121 (and E086), unguarded
\end{laincode}
\end{example}

\section{Enum types}
\label{sec:types.enum}
\index{enum type}

\pnum
An enum type is a type with a finite, named set of values.  Each variant
carries no associated data.  The grammar production is
\gramref{enum-declaration} (Annex~A).

\pnum
An enum type is represented by an unsigned integer type whose values \(0, 1, \ldots, n-1\)
are its variants in declaration order. The integer is the smallest that holds the variants
(\S\,\ref{sec:mem.adt-layout}) unless the declaration states a \textit{backing width}
between the type name and the body:

\begin{example}
\begin{laincode}
type TokenKind u16 { Ident, Number, Punct }
assert @sizeof(TokenKind) == 2
\end{laincode}
\end{example}

\pnum
A record that stores an enum has a layout that depends on the enum's width. With a backing
width, adding a variant leaves that layout where it is, and a variant that no longer fits
makes the declaration ill-formed instead of the enum silently wider.

\begin{constraint}
  A backing width shall be \lain{u8}, \lain{u16}, \lain{u32} or \lain{u64}, and shall appear
  only on an enum none of whose variants carries a payload. A backing width \lain{uN} holds at
  most \(2^N\) variants. A violation is \illformed{}~(\diagcode{E100}).
\end{constraint}

\begin{example}
\begin{laincode}
type Sign i8 { Minus, Plus }             // ERROR: E100
\end{laincode}
\begin{laincode}
type Shape u8 { Dot, Circle { r u32 } }  // ERROR: E100
\end{laincode}
\end{example}

\pnum
Enum values are accessed as \lain{TypeName.VariantName}.

\begin{constraint}
  Using \lain{==} or \lain{!=} to compare enum values is \illformed{}.
  Enum values shall be compared using \lain{case} pattern matching
  (\S\,\ref{sec:15-match}).
\end{constraint}

\begin{note}
  The constraint on \lain{==} for enums reflects that the underlying tag
  representation is implementation-defined.  Pattern matching is always
  sound.
\end{note}

\section{Algebraic data types (ADTs)}
\label{sec:types.adt}
\index{algebraic data type}

\pnum
An ADT is a sum type in which each variant may carry associated fields.
A type declaration is classified as an ADT if at least one variant has
fields.  The grammar production is \gramref{enum-declaration} (Annex~A,
using the record-variant form).

\pnum
ADTs use a niche-based representation whenever a zero-cost encoding is
available; otherwise they are a tagged union: a tag beside a union of the variant payloads
(\S\,\ref{sec:mem.adt-layout} gives the tag's width). A payload's fields are stored as a
struct's are (\S\,\ref{sec:types.struct}), by decreasing alignment, unless the sum is
\tok{[ordered]} or reachable from an \lain{extern} signature.

\begin{note}
  \textbf{D-Niche aggressive multi-slot.}
  When the variant payload admits a \textit{niche}---a bit pattern that
  cannot occur in any valid value of the payload type---that niche is
  used to encode tag-less variants.  Only a sum with one
  payload-carrying variant, whose payload is a single field, can be
  encoded this way. The niche sources are the zero page for a pointer,
  the values outside its refinement for a constrained integer, the 254
  byte patterns outside \(\{0, 1\}\) for \lain{bool}, the values above
  the last variant for a plain enum that declares its width
  (\lain{type K u8 \{ A, B, C \}} leaves 3 to 255), and the slots a
  packed sum leaves unused when it is itself the payload. A slice is not a
  niche source, nor is a plain enum without a declared width, whose width
  (and so whose spare values) would change with its variant count, nor an
  enum that the signature of an \lain{extern} function reaches, since C may
  hand it any value of its width: a sum whose payload is one of them
  carries a tag. A value of an enumeration type is always one of its
  variants: no conversion produces one from an integer, and writing any
  other value into one is undefined (\S\,\ref{sec:unsafe.ub}).

  Whenever a sum is given a tag, the compiler emits \diagcode{W120} (a
  warning, never an error) with the reason. When the reason is the
  payload's spare values, the programmer may remove the tag by
  constraining the payload, by declaring a plain enum payload's width, or
  by choosing a payload type that has spare values; otherwise the tag is
  the cost of the shape. See
  \S\,\ref{sec:mem.adt-layout} for the full layout algorithm and its
  target dependencies.
\end{note}

\pnum
ADT values are constructed as \lain{TypeName.VariantName(args)} for
variants with fields, or \lain{TypeName.VariantName} for unit variants.

\pnum
ADT values are destructured via \lain{case} pattern matching
(\S\,\ref{sec:15-match}).

\section{Pointer types}
\label{sec:types.pointer}
\index{pointer type}

\pnum
A pointer type \lain{*T} or \lain{const *T} is a raw memory address.
Pointer operations require an \lain{unsafe} block (\S\,\ref{sec:18-unsafe}).

\pnum
The ownership modes for pointer types are:

\begin{longtable}{@{}llll@{}}
\toprule
\textbf{Lain syntax} & \textbf{Mode} & \textbf{C99 type} & \textbf{Linear?} \\
\midrule
\endfirsthead
\toprule
\textbf{Lain syntax} & \textbf{Mode} & \textbf{C99 type} & \textbf{Linear?} \\
\midrule
\endhead
\bottomrule
\endlastfoot
\lain{*T}     & shared (read-only) & \texttt{const T*}  & no \\
\lain{var *T} & mutable            & \texttt{T*}        & no \\
\lain{mov *T} & owned              & \texttt{T*}        & yes \\
\end{longtable}

\begin{constraint}
  Dereferencing a pointer or taking the address of a variable shall occur
  only inside an \lain{unsafe} block.  Pointer dereference in safe code is
  \illformed{}~(\diagcode{E060}).
\end{constraint}

\section{Constrained types}
\label{sec:types.constrained}
\index{constrained type}

\pnum
A constrained type is a type annotated with a value range constraint:

\begin{center}
\textit{T} \textit{op} \textit{bound}
\end{center}

where \textit{op} $\in \{$\lain{>=}, \lain{<=}, \lain{>}, \lain{<},
\lain{==}$\}$ and \textit{bound} is an integer literal.

\pnum
Constrained types are used in function return types and parameter types to
declare value range invariants that the value range analysis
(\S\,\ref{sec:13-vra}) shall enforce.

\begin{example}
\begin{laincode}
func nonzero_divisor() int >= 1 {
    return 42   // VRA verifies: 42 >= 1 holds
}
\end{laincode}
\end{example}

\pnum
The constraint is part of the function signature, not the type system's
nominal identity.  Two constrained types with the same base type are
assignment-compatible.

\section{Type compatibility and equivalence}
\label{sec:types.compat}
\index{type equivalence}
\index{type compatibility}

\pnum
Lain uses \textbf{nominal type equivalence}: two types are the same if and
only if they have the same declared name.

\pnum
Two types $T_1$ and $T_2$ are \textit{compatible} for an expression context
if:
\begin{itemize}

  \item $T_1$ is an integer type of lower rank than $T_2$ (implicit

\begin{constraint}
  An expression of type $T_1$ used in a context requiring type $T_2$, where
  $T_1$ and $T_2$ are not compatible, is \illformed{}.
\end{constraint}

\pnum
The operators \lain{==} and \lain{!=} are defined for:
\begin{itemize}
  \item primitive numeric types;
  \item \lain{bool};
  \item pointer types.
\end{itemize}
They are not defined for struct types, array types, or enum types.
